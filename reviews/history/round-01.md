## Blocking Issues

### B1. 첫 고객과 과거 행동 증거가 없다

- 문제: 여러 고객군을 동등한 대상으로 두고 통합의 어려움을 확정적으로 서술한다.
- 근거: §1–2에는 역할·최근 통합 사례·빈도·시간·재작업 기록이 없다.
- 왜 중요한가: 핵심 낭비가 배선·드라이버 구현이라면 자연어 명세 작성이 해결하는 비중이 작을 수 있다.
- Writer가 문서 수정으로 해결 가능한가: **일부 가능**. ICP/JTBD를 검증 후보로 좁히고 ASSUMPTION 표시와 실험을 정의할 수 있다. 고객 Pain 증명은 **문서 수정으로 해결 불가**.
- 필요한 수정 또는 실제 검증: 첫 역할·장비 조건·반복 상황·제외 고객을 명시한다. 해당 후보 3명에게 최근 통합 1건씩의 작업 기록을 요청하여 매뉴얼 해석, 배선/드라이버, 명세 작성, 검토/테스트 시간을 분리한다. 인터뷰 수와 판정 기준은 계획값이며 조사 결과로 쓰지 않는다.

### B2. 기존 대안 대비 가치와 무수정의 경계가 불명확하다

- 문제: 제안도 구현된 Adapter를 전제로 하지만 §5는 기존 Connector 방식과 과도하게 대조한다.
- 근거: §4.2의 Operator 무수정, §7의 미리 구현된 Adapter, §14의 처음 보는 장비 메시지가 어느 코드·설정까지 고정하는지 설명하지 않는다.
- 왜 중요한가: 장비별 코드 변경을 Adapter/펌웨어로 옮긴 데모는 일반화나 고객 비용 절감을 증명하지 못한다.
- Writer가 문서 수정으로 해결 가능한가: **일부 가능**. 지원 프로토콜·명세 표현 범위와 비교 설계는 가능하다. 실제 순절감·대안의 불충분성은 **문서 수정으로 해결 불가**.
- 필요한 수정 또는 실제 검증: 이미 지원되는 Serial 명령 규약 내에서만 무수정이라고 한정한다. 새 프로토콜/드라이버 개발을 제외한다. 같은 장비 자료로 수동 명세/폼, 현재 스크립트·SDK/워크플로 방식, 자연어 초안 방식을 비교하고 검토·오류 수정·장비 테스트를 포함한 총 작업 시간을 측정한다. 경쟁 제품의 미검증 기능 여부는 단정하지 않는다.

### B3. 안전 승인과 정지·테스트·재시도 정책이 충돌한다

- 문제: 위험 행동 승인 원칙만으로 사전 테스트와 운영 쓰기 모두를 안전하게 제한할 수 있는지 판정할 수 없다.
- 근거: §8의 `emergency_stop → DANGEROUS / 사용자 승인 필요`, §10의 등록 전 기능 테스트, §11의 선택 사항인 실행 로그·Risk Level, Day 11의 안전 구현.
- 왜 중요한가: 긴급 정지에 대화 승인을 기다리게 하거나, 테스트 경로가 운영 gate를 우회하거나, 응답 유실 후 쓰기를 재전송하면 데모 자체의 안전 경계가 깨진다.
- Writer가 문서 수정으로 해결 가능한가: **가능**. 정책·비범위·수용 조건은 문서로 고칠 수 있다. 물리 안전 동작 확인은 별도 실제 검증이다.
- 필요한 수정 또는 실제 검증: 로컬 물리 정지/인터록을 Agent와 독립시킨다. 일반 정지와 재가동을 구분한다. 사람 확인→제한된 장비 테스트→검증 상태 등록의 순서를 명시한다. 읽기/쓰기·승인 대상 명세 버전·범위 검증·감사 기록을 Must에 둔다. 쓰기 timeout의 결과 불명 상태에서는 자동 재전송·후속 동작을 중단하고 사람이 확인한다. 안전 경계를 첫 주 기능 실행보다 먼저 설계한다.

### B4. 범위와 일정에 최소 검증 경로가 없다

- 문제: 컨베이어·로봇팔 통합과 선택 기능이 핵심 가설 검증을 압도할 가능성이 있다.
- 근거: §7은 Serial/GPIO 모두 MVP, §11은 GPIO 선택 사항, §16은 동적 Tool 포함 여부를 다시 연다. §13은 두 번째 주에 로봇팔·안전·UI를 개발한다.
- 왜 중요한가: 일주일 통합 검증을 확보하지 못하고 기구 조립에 일정이 소진될 수 있다.
- Writer가 문서 수정으로 해결 가능한가: **가능**. 실제 준비 여부·팀 가용성 확인은 외부 증거가 필요하다.
- 필요한 수정 또는 실제 검증: 기능은 검증된 온보딩과 등록 기능의 발견·조합 2개로 고정한다. Serial 하나와 서로 다른 두 저위험 장비를 최소 테스트베드로 허용한다. 로봇팔·컨베이어는 준비 조건을 충족할 때만 선택하고 실패 시 최소 장비로 축소한다. 3명 기본 역할/4명 추가 역할과 통합 주간 전 동결 조건, Must/Should/Later/Do Not Build 및 재검토 조건을 일관되게 작성한다.

### B5. 합격·실패와 Agent/MCP 필요성을 감사할 기준이 없다

- 문제: 성공 체크리스트는 있으나 하드코딩한 조합과 실제 신규 장비 발견을 구분하지 못한다.
- 근거: §10의 고정된 5단계 실행, §14–15의 성공 선언에는 초기 Registry, 코드·프롬프트 고정 증거, 실패 trace, 장비 실제 상태 확인 방법이 없다.
- 왜 중요한가: 발표 성공이 핵심 가설 검증으로 오인될 수 있다. 고정 조건 실행은 매 단계 LLM 판단 없이 처리할 수 있다.
- Writer가 문서 수정으로 해결 가능한가: **가능**. 테스트 결과 자체는 실제 실행 전 미확인으로 남겨야 한다.
- 필요한 수정 또는 실제 검증: 데모 전 Operator/Setup/Adapter/펌웨어 및 시스템 프롬프트를 고정하고 허용 변경을 명세·Registry·사용자 입력으로 제한한다. 미등록 장비의 추가 전후 조회, 실제 장비 상태, 실행 기록과 변경 diff를 증거로 남긴다. 누락·타입/범위 오류·미지원 프로토콜·미승인/미검증 호출·연결 실패·쓰기 응답 유실의 기대 결과를 표로 정하고 반복 횟수와 통과 기준을 계획값으로 명시한다. MCP는 고정 discovery/invoke 계약을 통해 Registry 변경을 Operator 코드와 분리하는 경계로 설명한다. LLM은 명세 초안·누락 질문·등록 기능 선택에 한정하고 승인 후 실행 순서·조건 분기·정책·종료는 결정적으로 처리한다.

## ICP / JTBD

현재 ICP는 선택 전 후보 목록이다. 첫 검증 대상으로 예를 들어 이미 텍스트 Serial 장비를 다루며 실험 장치를 반복 교체하는 소규모 연구실의 장비 통합 담당자를 좁혀볼 수 있다. 이는 고객 확인 사실이나 새로운 제품 방향 확정이 아니다.

JTBD는 “새 장비를 기존 실험 순서에 붙이고 연결·기능 검증 기록을 남겨 다음 실험을 시작한다”처럼 고객 완료 결과로 표현할 수 있다. 비전문가도 매뉴얼 없이 통합할 수 있다는 주장은 현재 근거가 없다.

## Pain Evidence

Confirmed:

- 기획서가 자연어 명세·검증·등록·MCP 실행을 제안한다는 문서상 사실만 확인된다.
- 고객 인터뷰나 실측 자료는 기획서에 제시되지 않았다. 이는 고객 문제가 없다는 반증도 아니다.

Assumptions:

- 새 장비 통합이 반복되고 충분한 비용을 발생시킨다.
- 그 비용 중 명세 작성과 기존 작업 연동이 유의미한 비중이다.
- 사용자가 안전한 명세 초안을 만들 만큼 정확한 연결 정보와 명령 의미를 제공할 수 있다.
- 검토·테스트를 포함해도 자연어 방식이 총비용을 줄인다.

Missing evidence:

- 같은 역할에서 반복되는 과거 사례, 기존 코드/작업 기록, 단계별 소요 시간, 오류와 재작업, 실제 참여 의향의 행동 근거.
- 현재 대안과 비교한 총 작업 시간 및 수정 횟수. 수치 목표는 아직 합의해야 할 실험 기준이다.

## Alternatives / Differentiation

비교 후보는 현재 담당자의 스크립트/장비 SDK, 수동 DeviceSpec/입력 폼, 기존 workflow/agent 도구 및 현장 PLC/SCADA 연동이다. 각 대안이 실제 고객 장비를 지원하는지는 미확인이다. 이 리뷰는 특정 제품의 최신 기능이나 경쟁 우위를 조사·확정하지 않았다.

방어 가능한 가설은 “지원되는 Adapter 범위에서 명세 초안 작성과 기능 재발견 비용을 줄인다”이다. 자연어·MCP·안전 계층 자체가 독점적 차별이라는 주장은 삭제하거나 ASSUMPTION으로 낮춘다. 비교 실험에서 현 대안이 더 빠르고 충분하면 중복 Build를 보류해야 한다.

## MVP Scope

### Must

1. 자연어 설명→명세 초안/누락 질문→구조·의미/안전 검증→사람 검토→제한된 실제 테스트→Registry 등록.
2. 기존 장비와 신규 두 번째 장비를 고정 generic MCP 계약으로 발견하고 승인된 최소 조합을 실행.

Serial 1종, 지원 명령 규약, 결정적 gate·최소 로그·실패 종료는 두 기능을 성립시키는 필수 조건이다.

### Should

- 핵심 테스트 통과 후 표시 편의 개선. GPIO·웹 UI는 필수 경로로 만들지 않는다.

### Later

- 추가 Adapter, 로봇팔 고난도 조작, workflow 저장, 동적 Tool, 매뉴얼/PDF 입력, 범용 조건 자동화.

### Do Not Build

- 임의 Python/Shell/PLC 코드의 생성·장비 직접 실행.
- 새 통신 프로토콜의 자동 발명, 모든 장비 지원, PLC/실시간 안전제어 대체, 검증되지 않은 기능의 무승인 실행.
- MVP 중 UI·Vision·Digital Twin·복잡한 다중 Agent 확장. 제외 이유와 재검토 조건을 원문에도 남긴다.

| 3. 고정 Adapter/명세가 두 번째 장비를 표현한다 | 무수정 온보딩 주장이 깨짐 | 예시 YAML만 있음 | 두 실제 장비 명령 문서를 고정 계약에 수작업 대입하고 부족 필드 확인 |
| 4. 설명과 승인만으로 위험을 정확히 분류할 수 있다 | 잘못된 물리 동작 가능 | 코드 gate 원칙만 있음 | 장비 담당자가 허용 동작·정지·테스트 조건을 먼저 검토 |
| 5. 팀·장비가 1주 핵심 구현/1주 검증에 준비돼 있다 | 통합 검증 시간 상실 | 일정 초안만 있음 | 첫 착수 전 역할 가용성·장비 확보·기존 통신 동작 증거 확인 |

## Safety / HITL

§8의 코드 강제와 로컬 제어기 책임은 유지한다. 비상정지 승인 대기는 수정해야 한다. Setup의 초안 생성 권한과 등록 전 시험 권한, Registry 활성화, Operator 쓰기 승인을 구분하고 미검증·변경된 명세는 운영 호출에서 차단한다. 명령/파라미터·대상·버전에 묶인 승인과 쓰기 결과 불명 상태의 중단, 최소 trace가 필요하다. 안전 관련 정책을 적었다는 사실은 장비 안전 검증 통과가 아니다.

## Two-week Feasibility

- Hardware risk: 장비 준비·펌웨어 명령 지원·정지 수단이 미확인이다. 구매 전제를 추가하지 말고 가용한 두 저위험 장비로 줄일 수 있어야 한다.
- Software risk: 자연어 초안과 질문·고정 계약 중심으로 좁힐 수 있다. GPIO/UI/동적 Tool을 함께 개발하면 검증 범위가 늘어난다.
- Integration risk: 현재 일정은 두 번째 주에도 핵심 개발이 계속된다. 첫 주 말 최소 두 장비 경로 동결, 둘째 주 반복/실패 검증을 목표로 재배치한다.
- 3~4명 가용성과 실제 장비 준비가 확인되기 전 2주 완료를 확정하지 않는다.

## Demo Validity

“이 데모가 정말 핵심 제품 가설을 증명하는가?”에 대한 현재 답은 **방향은 맞지만 증거 통제가 부족하다**이다.

첫 장비만 있는 초기 상태, 두 번째 장비 명세가 사전에 Registry/프롬프트에 들어 있지 않았다는 확인, 코드 고정, 실제 테스트 후 등록, 재발견 및 두 장비 조합 실행을 모두 남겨야 한다. 지원 프로토콜과 준비된 장비 펌웨어는 공개한다. 로봇팔을 LED/부저 등으로 줄여도 두 번째 장비의 등록·발견·사용이 실제라면 제한된 기술 가설은 검증할 수 있다. 고객의 Pain·시간 절감·산업 현장 안전성은 이 데모만으로 증명되지 않는다.

## Final Recommendation

문서로 해결할 B1–B5의 범위·정책·시험 설계를 먼저 수정하고 새 Reviewer context에서 재평가한다. 그 뒤에도 고객 과거 행동 증거, 대안 대비 순절감, 실제 장비 준비와 계약 적합성이 없으면 INVESTIGATE를 유지한다. 최우선 실제 검증은 좁힌 후보의 최근 통합 사례와 단계별 비용 확인이며, 문제 비중이 낮거나 기존 대안이 충분하면 구현을 보류한다. 문서 품질 향상을 GO나 실제 실행 성공으로 간주하지 않는다.
