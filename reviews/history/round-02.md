## Blocking Issues

### B1. 첫 ICP의 실제 반복 Pain과 병목 비중이 확인되지 않았다

- 문제: 고객 역할은 좁혀졌지만 그 집단이 제안한 구간에서 충분한 낭비를 겪는다는 증거가 없다.
- 근거: §1은 현재 업무와 병목을 ASSUMPTION으로 쓰며, §2는 최근 통합 기록·빈도·단계별 시간·재작업 실측 부재를 명시한다.
- 왜 중요한가: 배선·펌웨어·기구 보정이 대부분의 비용이라면 명세 초안 생성은 고객이 해결하고 싶은 가장 중요한 일이 아닐 수 있다. 기술 데모 성공으로 이 문제를 해소할 수 없다.
- Writer가 문서 수정으로 해결 가능한가: **불가.** 가정 표시와 검증 계획은 이미 충분하며 더 단정적인 문장으로 바꾸면 오히려 증거를 왜곡한다.
- 필요한 실제 검증: §5대로 같은 ICP 후보 3명의 최근 실제 통합 사례, 코드/메모 등 물증, 반복 빈도, 구간별 소요·재작업을 확인한다. 기억에 의존한 추정과 기록 기반 측정을 구분한다. 제안한 2명 이상 반복 사례·25% 비중은 실험 전 확정할 탐색 기준이지 시장 검증의 보장은 아니다.

### B2. 기존 대안 대비 순가치와 비용을 입증하지 못했다

- 문제: 수동 명세/폼이나 재사용 가능한 기존 스크립트보다 총시간·총비용이 줄어드는지 모른다.
- 근거: §3의 대안은 비교 후보이며 실제 비교 결과가 없다. §5·10은 모델, 가격, 처리량, 예산과 건당 비용을 미확정으로 남긴다.
- 왜 중요한가: 자연어 초안의 빠른 생성이 검토·수정 증가로 상쇄되면 도구를 추가할 이유가 없다. planning guide의 중복·비용 관문을 통과하지 못한다.
- Writer가 문서 수정으로 해결 가능한가: **불가.** 계산식과 비교 설계가 있어도 실제 측정값이 생기지는 않는다.
- 필요한 실제 검증: 동일 난이도·자료·완료 품질 조건에서 현재 방식, 수동 명세/폼, 자연어 초안을 교차 순서로 비교한다. 입력부터 검토·수정·장비 시험·연동 완료까지 전 시간을 기록하고 중도 실패도 포함한다. 실제 모델을 고르기 전 Wizard-of-Oz는 고객 가치 가능성만 살피며 실제 모델 비용/성능을 입증했다고 세지 않는다. 측정된 작업 시간과 확인한 사용량·단가로 정상 및 재작업 비용을 계산하고 예산을 확정한다. 제안 20% 절감 기준은 사전 확정 후 적용한다.

### B3. 두 실제 장비의 계약 적합성과 제한 시험 준비가 확인되지 않았다

- 문제: 고정 Adapter/명세로 두 번째 장비를 표현하고 안전하게 시험할 수 있는지, 이를 담당할 인력이 있는지 아직 확인되지 않았다.
- 근거: §2·9·10은 장비 보유·명령 지원·담당자 가용성이 미확인이라고 밝힌다. §6의 framing/응답 규칙도 장비 자료로 확정해야 한다.
- 왜 중요한가: 신규 파서·펌웨어가 필요하면 무수정 가설의 범위 밖이며, 준비 작업이 길면 2주 통합 검증이 무너진다. 안전 책임자나 상태 확인 수단 없이 실장비 테스트를 시작할 수 없다.
- Writer가 문서 수정으로 해결 가능한가: **불가.** 지원 범위와 축소/중단 기준은 이미 명시되어 있다. 실제 자료·가용성 확인이 필요하다.
- 필요한 실제 검증: 두 저위험 장비의 기존 매뉴얼·명령 자료를 고정 계약에 수작업 대입한다. 기존 수단으로 연결·상태 확인·로컬 정지가 가능한지 담당자가 확인하고 실제 시험 허용 범위를 정한다. 새 코드가 필요하면 지원 범위 밖으로 기록하고 장비를 축소한다. 두 실제 장비와 3~4명 가용성이 확인되지 않으면 일정 개시를 보류한다.

## Alternatives / Differentiation

§3은 기존 스크립트/SDK, 수동 명세/폼, workflow/agent 도구, 해당 현장의 PLC/SCADA를 비교 대상으로 둔다. 특정 제품의 기능 부재나 우월성을 확정하지 않아서 과장 주장은 없다.

방어할 후보는 “검토 가능한 계약과 시험 기록을 유지하면서 총 통합 작업 부담을 줄인다”는 결과다. 아직 차별화가 입증되지는 않았다. 가장 가까운 대안인 수동 명세/폼과 비교해야 자연어 기능의 추가 가치를 분리할 수 있다. 기존 도구로 충분하다는 결과가 나오면 Build를 보류해야 한다.

## MVP Scope

### Must

- 자연어 초안→결정적 검증→사람 검토→제한 실제 시험→활성 등록.
- 기존/새 장비의 MCP 재발견과 승인된 짧은 조합의 실제 실행.
- 이를 위한 고정 Serial Adapter/계약, Registry, validation/policy/executor, 실패 종료·승인·최소 기록.

### Should

- 필수 경로와 실패 테스트 통과 후 표시 편의만 개선.

### Later

- 다른 Adapter, Dynamic MCP Tool, 웹 UI, workflow 저장, 문서 자동 추출, 범용 조건 자동화와 복잡한 로봇 조작.

### Do Not Build

- 임의 실행 코드 생성, 프로토콜 발명, PLC 대체, 무인 운영, 미검증 기능 실행, 프롬프트만의 안전 제어, 이번 MVP의 Vision/Digital Twin/복잡한 다중 Agent.

범위 분류가 두 핵심 기능에 일관된다. 컨베이어/로봇팔을 필수로 두지 않은 최소 두 저위험 장비 데모는 핵심 검증을 보존하는 축소다.

## Safety / HITL

등록 전 시험과 운영 실행 권한, 대상·버전·인자·계획에 묶인 승인, 변경 시 승인 무효화가 구분되어 있다. 쓰기 응답 유실을 결과 불명으로 종료하고 후속 실행·자동 재전송을 멈추는 조건도 적절하다. 독립 로컬 비상정지와 재가동의 새 승인을 분리하고 있어 대화 승인이 정지를 막는 구조를 요구하지 않는다.

이것은 제품 조건의 명시이며 코드 강제나 실물 안전 검증 완료가 아니다. 실제 장비 담당자 확인 및 §12의 전송 0회·정지·재가동 증거가 필요하다. 추가 안전 기능을 상상해 문서 범위를 확대할 필요는 없다.

## Two-week Feasibility

- Hardware risk: 두 실제 장비의 보유·기존 통신·상태/정지 확인이 아직 없어 최대 불확실성이다. 최소 저위험 장비로 축소하거나 실장비 가설 검증을 중단한다는 기준은 적절하다.
- Software risk: 두 기능이더라도 명세 검증·시험 권한·승인·결과 불명 처리는 생략할 수 없다. 단일 Adapter/CLI/유한 계획과 부가 기능 제외로 범위는 제한되어 있다.
- Integration risk: 첫 주 전체 경로와 실패 처리를 연결하지 못하면 둘째 주가 개발로 잠식될 수 있다. §10의 동결·중단 기준을 실제로 적용해야 한다.
- 인원 책임과 일정은 검토 가능한 수준이나 완료 가능성을 입증하지 않는다. 사전 조사/장비 확인을 2주 구현 밖의 선행 gate로 명시했으므로 조건부 계획으로 수용한다.

## Demo Validity

“이 데모가 정말 핵심 제품 가설을 증명하는가?”에 대한 답은 **기술 가설의 제한된 사례를 시험하는 데 적합하지만, 아직 실행되지 않았고 고객 가치를 증명하지는 않는다**이다.

§6·11의 허용 변경 범위와 전후 hash, 초기 Registry, 실제 테스트 후 활성 등록, 같은 Operator 재조회는 코드 무수정 주장을 감사할 수 있게 한다. 새 장비 매핑을 프롬프트/예시에 미리 넣지 않도록 하고 독립 검수를 요구하는 것도 적절하다. 동결 후 비작성자 장비 선택이 가능하지 않으면 일반화 한계를 그대로 남겨야 한다.

센서 읽기와 표시 장치 실행의 짧은 조합은 새 장비 발견·사용이라는 최소 기술 가설을 보존한다. 임의 프로토콜 지원이나 산업 현장 자동화 성공까지 확대할 수 없다. 같은 두 장비의 정상 3회는 좁은 반복성 증거이며 전반적 신뢰성 증거가 아니다. §12가 이 한계를 이미 명시한다.

## Final Recommendation

**문서 수정으로 해결할 핵심 blocker는 남아 있지 않다. 추가 Writer 수정은 필요하지 않으며 이번 반복은 INVESTIGATE로 종료하는 것이 타당하다.** 현재의 명확한 가설·조건부 범위·실험 계획을 GO의 근거로 바꾸면 안 된다.

다음 순서는 실제 사례로 Pain 확인 → 기존 방식/수동 명세 대비 순가치·비용 비교 → 두 장비 계약·시험 준비와 인원 확인이다. §5의 제안 기준을 결과 관측 전에 확정하고 물증·측정값·실패를 남긴 뒤 제품 Build 여부를 다시 판정한다. 증거가 아직 없다는 이유만으로 제품이 성립하지 않는다고 단정할 수 없으므로 HOLD도 현재 근거로는 이르다.

구현 전 반드시 답할 질문은 세 가지다: 이 담당자가 줄일 가치 있는 반복 비용을 이미 지불하는가, 기존 대안보다 검토 포함 순절감이 있는가, 고정 지원 범위와 실제 장비/담당자가 그 가설을 검증할 준비가 되어 있는가.
