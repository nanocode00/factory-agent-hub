## 1. 프로젝트 목표

### 동작 가능한 버티컬 AGENT 만들기

**내가 3개월 이상 직접 경험한 버티컬 도메인**에서 실제 사용자의 반복 업무를 해결하는 Agent를 만든다.

단순 모델 호출이 아니라 다음 요소가 연결된 **서비스**로 완성해야 한다.

- 도메인 규칙
- 도구
- 평가
- 사용자 입력과 결과/실패 안내
- 운영 가능한 실행 경로

## 2. 주제 검증 기준

가장 먼저 확인해야 하는 질문은 다음과 같다.

> 내가 그 도메인의 사용자·업무 흐름·예외 상황을 3개월 이상 경험했는가?

첫 체크포인트는 두 가지다.

1. **3개월 이상 경험**
   - 직접 겪은 사용자 상황을 설명할 수 있어야 한다.
   - 실제 업무 흐름을 설명할 수 있어야 한다.
   - 실제 예외 상황을 구체적으로 설명할 수 있어야 한다.
2. **반복 업무**
   - Agent가 줄일 수 있는 반복 작업을 정의한다.
   - 평가에 사용할 입력 **30건**의 기준을 잡는다.

## 4. 완료 정의 — 주장보다 증거

프로젝트 완료는 단순히 “돌아간다”라고 설명하는 것이 아니다.

다른 사람이 확인할 수 있도록 최소 다음을 남겨야 한다.

- 몇 건 중 몇 건이 **출력 계약**을 지켰는가
- 실패 시 어떤 **실패 경로**로 떨어지는가
- 한 번 처리하는 데 드는 **품질·비용**은 얼마인가

즉 핵심 증거 축은 다음과 같다.

1. 출력 계약
2. 실패 경로
3. 품질·비용

## 5. 제출 서비스 구성

버티컬 Agent를 **운영 가능한 서비스** 형태로 제출한다.

화면, Agent API, MCP 도구, 관측·평가를 하나의 실행 경로로 연결한다.

> MCP는 제품 기능을 위한 **도메인 도구**이며 공개 데모 API가 아니다.

| 구분 | 요구사항 | 제출 증거 |
|---|---|---|
| **Vercel UI** | 사용자 입력 · 결과 · 실패 안내 | Vercel URL |
| **Cloud Run API** | `GET /health` · `POST /api/agent` | Cloud Run URL |
| **MCP 도구** | 도메인 데이터·행동을 `/mcp`로 제공 | 실제 호출 결과 |
| **Evidence loop** | Docker · Langfuse · Prompt Management · Evals 재측정 | README · `EVAL_REPORT` |

### API/MCP 경계

- `/api/agent`와 `/mcp`의 역할을 분리한다.
- 브라우저가 Cloud Run을 직접 호출한다면 README에 다음을 설명한다.
  - CORS
  - 인증
  - 비밀값 노출 방지 방식
