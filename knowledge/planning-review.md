## 0. 전체 핵심 한 장 요약

AI를 잘 쓰는 핵심은 모델 자체보다 **맥락을 주고, 좋은 질문을 하고, 결과를 검증하는 능력**이다. 기획에서는 여기에 한 단계가 더 필요하다. **만들 수 있는가(HOW)**보다 먼저 **만들 가치가 있는가(WHETHER)**를 확인해야 한다.

전체 흐름은 다음처럼 연결된다.

```text
좋은 요청
  ↓
R·O·R·E·C로 맥락과 기대를 명확히 함
  ↓
소크라테스식 대화(CAGV)로 빠진 가정과 질문을 드러냄
  ↓
실제 페인을 ICP/JTBD와 과거 행동(Mom Test)으로 검증
  ↓
기능을 덜어내고 핵심 범위를 1~2개로 좁힘
  ↓
hplan Build Gate에서 증거·중복·비용·비범위를 확인
  ↓
1장 Agent 기획서로 문제·사용자·핵심 기능·완료 정의를 고정
  ↓
입력·처리·출력·도구·HITL을 설계
  ↓
더미/공개 데이터로 happy path 프로토타입
  ↓
실행 결과로 검증 → 운영 지표와 실패 로그를 축적
```

기억해야 할 문장만 압축하면 다음과 같다.

- **좋은 답은 좋은 질문의 그림자다.**
- **AI는 명령을 받는 자판기가 아니라 맥락을 줘야 하는 동료다.**
- **결과 품질 = 대화(입력) 품질.**
- **기획자는 더하는 사람이 아니라 덜어내는 사람이다.**
- **기술 스택보다 문제 → 입력/출력 → 도구 순서다.**
- **자동화 자체가 목표가 아니라 사람 판단 전 단계를 줄인다.**
- **탐색·기획·검증은 느린 일이 아니라 비싼 사고를 막는 보험이다.**
- **AI는 필터, 현업은 최종 판정자다.**
- **HOW보다 WHETHER를 먼저 묻는다.**
- **증거·비용·비범위·결정을 기록하고 나서 만든다.**

# Part I. AI에게 좋은 요청을 만드는 법

## 1. AI는 '명령'이 아니라 '대화'다

### 1.1 자판기 모드 vs 동료 모드

**자판기 모드**는 한 줄 명령을 던지고 한 번의 출력으로 끝낸다.

```text
보험금 분석해줘.
```

이 방식은 맥락이 없고, 결과가 마음에 들지 않으면 곧바로 "AI가 별로다"라는 결론으로 가기 쉽다.

**동료 모드**는 AI를 잠재력은 높지만 내 업무 맥락을 모르는 동료처럼 다룬다. 목적, 대상, 판단 기준, 제약, 피해야 할 것, 결과 형식을 알려주고 출력에 피드백을 주면서 다듬는다.

핵심은 AI가 사용자의 머릿속 맥락을 읽지 못한다는 점이다. 따라서 결과가 아쉬울 때는 모델을 탓하기 전에 **요청에 필요한 정보가 충분했는지**부터 본다.

### 1.2 우리가 통제할 수 있는 변수

| 영역 | 통제하기 어려운 것 | 통제할 수 있는 것 |
|---|---|---|
| AI 모델 | 모델의 기반 성능 | 맥락, 명확한 요청 |
| 결과 형식 | 모델의 기본 출력 방식 | 표, 3문장, 불릿 등 형식 지정 |
| 정확성 | 학습 데이터 한계 | 근거 요구, 검증 지시 |
| 깊이 | 모델 자체의 추론 능력 | 분석 절차와 판단 기준 제시 |

### 1.3 역할 뒤집기: AI가 나를 인터뷰하게 한다

생각이 정리되지 않았을수록 바로 답을 요구하지 않는 편이 좋다.

```text
신상품 기획을 도와줘.
그 전에, 더 좋은 도움을 주려면 나에게 무엇을 물어봐야 할지 먼저 질문해줘.
```

AI의 질문에 답하는 과정 자체가 요구사항을 명료하게 만든다. 특히 기획, 분석, 문제 정의처럼 시작점이 모호한 업무에서 효과적이다.

## 2. 좋은 요청의 뼈대

### 2.1 짧은 요청에는 4요소

간단한 일상 요청에는 다음 4가지만 있어도 품질이 크게 안정된다.

1. **누가** — 결과를 누가 읽거나 사용할지
2. **왜** — 목적이 무엇인지
3. **무엇을** — 정확히 무엇을 만들거나 바꿀지
4. **형식** — 어떤 출력 형태를 원하는지

예시:

```text
(누가) 신입 행원 교육용으로,
(왜) 약관을 쉽게 이해시키려고,
(무엇을) 이 약관 제15조를,
(형식) 중학생도 알 만한 3문장으로 풀어줘.
```

가장 자주 빠지는 것은 **왜(목적)**와 **형식**이다.

### 2.2 복잡·반복 업무에는 R·O·R·E·C 5요소

| 요소 | 의미 | 핵심 질문 | 예시 |
|---|---|---|---|
| **Role** | 역할 | 누구처럼 답해야 하나? | 베테랑 여신 심사역 |
| **Objective** | 목표 | 무엇을 얻고 싶은가? | 핵심 재무 리스크 식별·요약 |
| **Reasoning** | 판단/분석 전략 | 어떤 순서와 기준으로 볼 것인가? | 비율 계산 → 비교 → 정렬 |
| **Expectations** | 기대치 | 어떤 형식·품질·금지사항인가? | 표, 출처 명시, 불확실 표시 |
| **Context** | 맥락 | 무엇을 알고 시작해야 하나? | 공시, 업종 평균, 제약 |

역할은 마법 주문이 아니라 **관점을 좁히는 장치**다. `넌 전문가야`만 쓰기보다 역할과 구체 맥락을 함께 줘야 한다.

Reasoning은 모델의 내부 사고를 요구하는 것이 아니라, 사람이 검증할 수 있도록 **판단 순서·기준·산출 단계를 명시하는 것**으로 이해하면 된다.

### 2.3 5요소 완성형 예시 — 기업 재무 리스크 요약

```text
[Role]
당신은 기업 재무를 분석하는 베테랑 여신 심사역이다.

[Objective]
주어진 공시에서 핵심 재무 리스크를 식별·요약한다.

[Reasoning]
1) 부채비율·유동비율·이자보상배율·영업현금흐름을 계산한다. 검산값을 함께 둔다.
2) 동종업계 평균과 비교해 이상치를 찾는다.
3) 주석에서 우발부채·특수관계인 거래를 점검한다.
4) 위험 신호를 심각도 순으로 정리한다.

[Expectations]
[지표 | 값 | 업종평균 | 판정] 표로 작성한다.
모든 수치에 출처를 명시한다.
확실하지 않으면 '확인 필요' 또는 '불확실'로 표시한다.
형식에 안 맞지만 중요한 발견이 있으면 마지막에 별도로 적는다.

[Context]
분석 대상 공시=(...)
업종 평균=(...)

바로 답하지 말고 접근법을 먼저 정리한 뒤 부족한 데이터를 물어봐.
결과를 낸 뒤 가장 불확실한 항목을 스스로 반박해줘.
```

### 2.4 중요한 업무에 습관적으로 붙일 안전 문장

```text
수치·주장에는 근거(출처)를 함께 적어라.
확실하지 않으면 '불확실' 또는 '확인 필요'라고 표시하라.
```

특히 금융처럼 오류 비용이 큰 영역에서는 **근거 명시 + 불확실 표시 + 사람 검증**을 한 세트로 본다.

# Part II. 소크라테스식 AI 대화법

## 3. CAGV: Context → Analyze → Generate → Validate

많은 사용자가 **Generate**부터 바로 시작한다. 그러나 중요하거나 복잡한 업무는 다음 4단계를 거치는 편이 안전하다.

### 3.1 C — Context

먼저 판을 깐다. 역할, 목표, 배경, 대상, 데이터, 제약을 준다.

```text
[Role] 보험 상품 리스크를 보는 베테랑 컴플라이언스 담당자
[Objective] 저축성 보험 약관 초안에서 불완전판매·민원 소지를 사전에 줄이기
[Context] 주 타깃 고객 50대 이상, 과거 중도해지 환급금 민원 다수, 판매 강조점은 안정적 수익
(약관 원문)
```

### 3.2 A — Analyze

성급하게 결과를 생성하지 말고 문제를 구조화하게 한다.

```text
바로 문제점을 나열하지 말고 먼저
1) 이 약관을 검토할 때 어떤 관점에서 봐야 하는지
2) 더 정확히 보려면 나에게 무엇을 물어야 하는지
알려줘.
```

Analyze의 목적은 정답을 받는 것이 아니라 **빠진 변수와 전제를 드러내는 것**이다.

### 3.3 G — Generate

분석과 추가 답변을 바탕으로 실제 산출물을 만든다.

```text
지금까지의 맥락을 바탕으로 오해·분쟁 소지가 있는 조항을
[조항 | 오해소지 | 권장설명] 표로 정리해줘.
원문 근거를 함께 표시하고 추정은 '추정'으로 표시해.
```

### 3.4 V — Validate

출력을 그대로 받아들이지 않고 반박, 출처 대조, 불확실성 확인을 시킨다.

```text
이 결과에서 네가 가장 자신 없는 항목은?
과하게 판단한 부분이 없는지 스스로 반박해줘.
각 근거가 실제 원문과 일치하는지도 표시해줘.
```

중요·고위험 업무에서는 **Analyze와 Validate를 생략하지 않는다.**

## 4. 소크라테스식 5가지 핵심 기술

| 기술 | 표어 | 언제 쓰나 | 예시 |
|---|---|---|---|
| ① 점진적 깊이 | 층층이 파고들기 | 복잡한 주제 탐구 | 큰 질문 → 한 요소 선택 → 시나리오 → 숨은 가정 |
| ② 제약 우선 | 천장을 먼저 때리기 | 현실성 점검 | "가능해?" 대신 "이 예산·시간에서 무엇이 깨지나?" |
| ③ 역질문 | AI가 나를 인터뷰 | 생각이 흐릿할 때 | "답하기 전 내가 안 준 정보 3개를 먼저 물어봐" |
| ④ 반박 검증 | 악마의 변호인 | 결론 검증 | "이 결론을 깨는 가장 강한 반례와 성립 조건은?" |
| ⑤ 다중 관점 | 여러 모자 번갈아 | 이해관계가 복잡할 때 | 고객·영업·준법·감독 관점으로 분리 평가 |

### 4.1 점진적 깊이

```text
리스크 요인을 알려줘.
→ 그중 유동성 리스크를 구체 시나리오로 보자.
→ 그 시나리오에서 우리가 놓치기 쉬운 가정은?
```

### 4.2 제약을 먼저 건다

```text
2주, 4명, 공개·더미 데이터만 쓸 수 있다.
이 조건에서 무엇이 가장 먼저 깨질지부터 말해줘.
```

### 4.3 역질문

```text
이 주제로 도와줘.
단, 답하기 전에 판단에 꼭 필요한데 내가 안 준 정보 3개를 먼저 물어봐.
```

### 4.4 악마의 변호인

```text
이 결론을 깨는 가장 강한 반례 1개와 그 성립 조건은?
그 반례가 성립해도 기존 결론이 유지되는지 평가해줘.
```

### 4.5 다중 관점

```text
이 변경안을
1) 고객
2) 영업현장
3) 준법
4) 감독당국
관점에서 각각 평가해줘.
그다음 관점들이 서로 충돌하는 지점만 따로 정리해줘.
```

AI의 반박은 최종 판정이 아니다. **AI는 토론 상대이고 판단은 사람에게 남는다.**

## 5. 기획 검증용 소크라테스 5유형 질문

Agent 기획 단계에서는 다음 다섯 유형을 특히 많이 사용한다.

1. **명료화** — 정의가 모호하지 않은가?
   - "심사역이라고 했는데 연차·업무 범위는?"
2. **가정 검사** — 전제가 사실인가?
   - "1시간 걸린다는 것은 측정값인가, 체감인가?"
3. **근거** — 사실과 추측을 구분했는가?
   - "그 페인이 실제라는 증거가 있나?"
4. **관점/대안** — 다른 해결책이면 기능이 불필요하지 않은가?
   - "기존 도구로 해결하면 이 기능은 없어도 되나?"
5. **함의** — 장기적으로 어디서 무너지는가?
   - "3개월 운영하면 먼저 문제가 생길 곳은 어디인가?"

좋은 검증은 빈칸을 없애는 것이 아니라 **어떤 빈칸이 중요한지 찾는 것**이다.

### 복붙 프롬프트 — 답하지 말고 질문부터

```text
나는 '[내 과제]'의 첫 버전을 기획하려 해.
바로 기획서나 결론을 만들지 말고, 내가 놓쳤을 가능성이 높은 질문 7개를 먼저 해줘.

다음 다섯 유형을 섞어줘.
1) 명료화
2) 가정 검사
3) 근거
4) 관점/대안
5) 함의

각 질문마다 다음을 함께 적어줘.
- 검증하려는 가정
- 답하지 않으면 생기는 리스크
- 답에 따라 바뀔 결정

내가 답하기 전에는 결론을 쓰지 마.
```

## 6. 결과를 정리할 때의 '판단 구조'

최종 결과를 받을 때는 단순 결론보다 무엇을 근거로 판단했는지 검토 가능한 형태를 요구한다.

```text
이제 정리해줘. 다음 구조를 사용해.
1) 한 줄 결론
2) 사용한 판단 기준 3개
3) 기준별 평가
4) 가장 강한 근거
5) 가장 약한 가정
6) 확신이 낮은 부분
7) 확인해야 할 데이터
8) 다음 액션

확실한 사실과 추정을 구분하고,
데이터가 부족하면 부족하다고 표시해줘.
```

# Part III. 바이브코딩 요청법

## 7. 일반 요청과 코딩 요청의 차이

코드는 글과 달리 "대충 그럴듯한 상태"가 곧 성공이 아니다. 실제로 실행되거나 실행되지 않는다.

| 구분 | 일반 요청 | 바이브코딩 요청 |
|---|---|---|
| 결과 성격 | 다소 어색해도 활용 가능 | 동작/비동작이 뚜렷함 |
| 모호함 허용 | 비교적 높음 | 낮음 |
| 추가 핵심 | 내용·형식 | 입출력 명세, 완료 정의, 검증 |
| 진행 | 한 번에 받아도 가능 | 작은 단계로 나눔 |
| 실패 대응 | 다시 작성 | 에러를 근거로 하나씩 수정 |

코드를 읽지 못하더라도 **입출력을 업무 언어로 명세하고 실제 출력으로 검증**할 수 있다.

---

## 8. 바이브코딩 요청의 5가지 요령

### 8.1 입·출력 명세

```text
입력: 종목코드
출력: 연도별 부채비율 표
```

### 8.2 한 번에 하나씩

큰 시스템을 한 번에 만들지 않고 **동작 확인 가능한 최소 단위**로 쪼갠다.

```text
1단계: 데이터만 불러오기
2단계: 계산 추가
3단계: 표시/예외 처리
```

### 8.3 완료 정의

감성적인 표현이 아니라 테스트 가능한 문장으로 쓴다.

```text
A사 종목코드를 넣으면 부채비율 표가 나오고,
표의 계산값이 공시 원문 값과 일치하면 완료.
```

### 8.4 실행 증거 요구

```text
실제로 실행해서 결과를 보여줘.
예시 2개로 테스트해줘.
수치가 있으면 계산에 사용한 원값과 계산 과정도 보여줘.
```

### 8.5 에러 복구

에러 메시지를 생략·요약하지 말고 그대로 전달한 뒤 여러 수정을 동시에 요구하지 않는다.

```text
아래 에러 메시지를 기준으로 원인을 설명해줘.
그다음 해결책을 한 번에 하나씩 적용해줘.
각 수정 후 다시 실행해 결과를 확인해줘.
```

---

## 9. 바이브코딩 체크리스트

- [ ] 입력과 출력을 업무 언어로 적었는가?
- [ ] 작업을 작은 단계로 쪼갰는가?
- [ ] 현재 단계의 완료 정의가 테스트 가능한가?
- [ ] "실행해서 결과를 보여줘"를 요청했는가?
- [ ] 수치라면 검산용 원값/계산 과정도 확인하는가?
- [ ] 에러가 나면 전체 메시지를 복사해 하나씩 수정할 준비가 되었는가?
- [ ] 마지막에 출처·반대근거·불확실성을 점검하는가?

핵심 리듬은 **작게 시작 → 실행 검증 → 에러를 하나씩 복구**다.

# Part IV. AI Agent 기획의 기본 사고

## 10. 만들 수 있다 ≠ 쓸모 있다 ≠ 팔린다

AI가 코딩, UI, 배포, 보일러플레이트, 문서 초안, 반복 작업의 비용을 크게 낮출수록 오히려 다음 판단의 가치가 커진다.

1. **무엇을 만들 것인가** — Discovery와 문제 정의
2. **왜 이것이 진짜 페인인가** — 검증과 가설
3. **만든 것이 가치가 있는가** — 성과와 측정
4. **누가 왜 쓰는가** — 사용자와 확산

도구가 쉬워졌다고 이 네 가지가 자동으로 해결되지는 않는다. 오히려 잘못된 방향으로 더 빨리 만들 수 있게 된다.

### 흔한 실패 흐름

```text
AI 시대니까 뭔가 만들자
→ 도구를 잡는다
→ 무엇을/누구를/왜 위한 것인지 모른다
→ 기능만 늘어난다
→ 나만 쓰는 데모 또는 포기
```

---

## 11. 기획자는 '덜어내는' 사람

좋은 기획은 기능을 많이 쓰는 문서가 아니라 **무엇을 지금 만들지 않을지 정하는 문서**다.

모든 기능에는 숨은 비용이 있다.

- 구현 시간
- 유지보수 비용
- 사용자 혼란
- 테스트 범위
- 실패 가능성
- 핵심 문제에 쏟을 집중력의 분산

### 남기기 기준

> "이 기능이 없으면 핵심 문제가 해결되지 않는가?"

그렇다면 1차 핵심에 남긴다. 아니라면 **Later/보류**로 이동한다. 보류는 삭제가 아니라 "지금은 아니다"이며, 이유를 한 줄 남긴다.

### Constraint-first

꿈은 크게 잡되 첫 버전은 제약을 먼저 적는다.

```text
기간: 2주
팀: 3~4명
데이터: 공개/더미 우선
핵심 기능: 1~2개
고객 영향 행동: 사람 승인 전 자동 실행 금지
```

---

## 12. 제품 개발 4단계와 검증을 건너뛸 때의 비용

```text
1. Discovery — 누구의 어떤 문제인가?
2. Plan      — 무엇만 만들고 무엇을 안 만들 것인가?
3. Build     — 실제 동작하는 최소 버전을 만든다.
4. Grow      — 정착·확산·운영 개선으로 이어간다.
```

| 생략한 단계 | 나중에 터지는 문제 | 비용 |
|---|---|---|
| 탐색 | 다 만든 뒤 아무도 안 씀 | 개발 기간 전체 낭비 |
| 기획 | 제작 중 범위가 끝없이 늘어남 | 미완성, 재작업, 번아웃 |
| 검증 | 틀린 결과가 운영에 들어감 | 신뢰 하락, 사고, 리스크 |

**탐색·기획·검증은 느린 일이 아니라 비싼 사고를 미리 막는 보험**으로 본다.

# Part V. Discovery — ICP와 JTBD

## 13. ICP: 누가 가장 강하게 겪는가

ICP(Ideal Customer/User Profile)는 넓게 잡을수록 문제가 흐려진다.

```text
X: 현업 직원
O: 기업 여신 1차 심사 3~7년차 심사역
```

역할, 연차, 상황, 반복 업무가 좁혀질수록 실제 페인을 찾기 쉬워진다.

## 14. JTBD: 그 사람이 끝내려는 일은 무엇인가

JTBD(Job To Be Done)는 기능이 아니라 **사용자가 끝내고 싶은 일**이다.

```text
X: 재무비율 계산기를 쓴다.
O: 흩어진 자료에서 위험 신호를 빠르게 파악해 심사 의견을 작성한다.
```

템플릿:

```text
[ICP]가 [상황]에서 [끝내려는 일]을 [더 빠르게/정확하게] 하도록 돕는다.
```

예시:

- 여신: 심사역이 공시에서 핵심 재무 리스크를 파악해 심사 의견을 작성
- 시황: WM·시황 담당자가 매일 아침 시장 변화를 한 장으로 요약·보고
- 약관: 신입 행원·상담 담당자가 고객 질문에 근거 조항을 찾아 정확히 답변

# Part VI. 페인 검증 — Mom Test와 증거

## 15. 의견보다 과거 행동을 묻는다

```text
X: 이런 도구 있으면 쓰실래요?
O: 지난주 이 업무를 몇 번 했나요?
O: 한 번 할 때 몇 분 걸렸나요?
O: 지금은 어떤 방법으로 해결하나요?
O: 급할 때 임시방편으로 무엇을 하나요?
```

진짜 페인의 강한 신호는 이미 사용자가 **시간, 수작업, 복붙, 엑셀, 임시 스크립트, 반복 확인 같은 우회 비용을 지불하고 있는가**다.

AI는 "무엇을 확인해야 할지"를 좁히는 필터로 쓰고, 현업 인터뷰와 실제 데이터가 최종 판정을 담당한다.

### 페인 증거로 좋은 것

- 반복 횟수(count)
- 평균 또는 p90 지연 시간
- 재작업률
- 수작업 단계 수
- 오류/누락 빈도
- 실제 우회 행동
- 이미 투입 중인 인력·시간·비용

# Part VII. hplan_codex — WHETHER before HOW

## 16. 핵심 철학

hplan_codex의 핵심은 에이전트를 곧장 구현하기보다 먼저 다음을 묻는 것이다.

```text
이걸 만들 가치가 있는가?
실제 페인의 증거가 있는가?
기존 도구와 중복되지 않는가?
운영 비용을 감당할 수 있는가?
어디까지 자동화하고 어디서 사람이 승인할 것인가?
무엇은 이번에 만들지 않을 것인가?
```

즉 **HOW보다 WHETHER가 먼저**다.

### 자료 내 표기 주의

원자료 앞부분에는 `5개 플러그인/28개 스킬`이라는 설명이 나오지만, 뒤의 딥다이브에서는 **hplan, oracle, atlas, forge, argus, muse의 6개 단계**와 합계 **43개 스킬**을 설명한다. 이 통합본은 상세 딥다이브의 구조인 **6단계/43스킬**을 기준으로 정리한다.

---

## 17. 6단계 라이프사이클

```text
게이트       발견        설계       실행       운영       학습
hplan   →   oracle   →   atlas  →   forge  →   argus  →   muse
  7           6            7          12          8          3
skills      skills       skills      skills      skills      skills
```

운영 과정에서 축적한 판단과 실패 로그(TK)는 다음 기획으로 돌아간다.

| 단계 | 핵심 질문 | 대표 산출물 |
|---|---|---|
| hplan | 만들 가치가 있나? | 증거 점수, COGS, 제외목록, 결정 로그 |
| oracle | 무슨 Agent를 만들까? | 기회 트리, 가정 검증, Build/Buy, HITL |
| atlas | 어떻게 구조화할까? | 3계층, 라우터, 메모리, RAG, 해자 |
| forge | 어떻게 스펙·출시할까? | PRD, instruction, prompt, eval, OKR |
| argus | 어떻게 측정·개선할까? | KPI, 신뢰성, 프리모템, A/B, 인시던트 |
| muse | 어떻게 계속 똑똑해질까? | PM 프레임워크, 결정 패턴, TK 엔진 |

## 18. HPLAN — Build Gate

### 18.1 `$brainstorm`

아이디어를 곧장 구현하지 않고 `GO / INVESTIGATE / HOLD`로 1차 분류한다.

- 입력: 아이디어
- 처리: 페인 가능성, 실현성, 중복 여부
- 출력: 판정, 이유, 다음 확인 항목

### 18.2 Evidence Rubric

인터뷰와 실제 증거의 강도를 점수화한다.

- 과거 행동인가?
- 물증이 있는가?
- 실측 수치인가?
- 여러 사람에게 반복되는가?

증거가 약하면 다음 단계로 서둘러 가지 않는다.

### 18.3 Interview Synthesis

여러 인터뷰에서 반복되는 페인, 우회 행동, JTBD를 묶어 공통 패턴을 찾는다. 한 사람의 강한 일화를 전체 사용자 문제로 확대하지 않도록 한다.

### 18.4 Do-Not-Build Registry

안 만들기로 한 기능을 이유와 함께 **append-only**로 남긴다.

```text
[보류/제외 기능]
- 자동 발송
- 이유: 고객 영향 행동이며 사람 승인 필요
- 재검토 조건: 현업 승인 프로세스가 정의되고 감사 로그가 확보될 때
```

이 기록은 6개월 뒤 같은 논쟁을 반복하지 않게 하는 자산이다.

### 18.5 COGS Sentinel

모델 호출량, 토큰, 캐시, 사용자 수 등을 바탕으로 운영 비용을 감이 아니라 숫자로 본다. 자료에서는 하루 1,000명 기준 p50/p90 비용·마진 계산 예시를 강조한다.

### 18.6 OST — Opportunity Solution Tree

```text
성과(Outcome)
  ↓
기회(Opportunity)
  ↓
솔루션 후보
  ↓
검증 실험
```

기능에서 시작하지 않고 원하는 성과에서 역으로 내려간다.

### 18.7 Decision Log + Handoff

왜 시작했는지, 왜 보류했는지, 무엇을 증거로 삼았는지, 다음 단계가 무엇인지 남긴다.

## 19. 시작 판정 3관문

### 관문 1 — 증거

진짜 페인이라는 구체 증거가 있는가?

- 시간
- 반복 수작업
- 임시방편
- 재작업
- 실제 우회 행동

### 관문 2 — 중복

이미 있는 시스템·도구·API로 해결 가능한 일을 다시 만들고 있지 않은가?

### 관문 3 — 비용

예상 처리량에서 모델 비용, 사람 검토 시간, 운영비를 감당할 수 있는가?

세 관문 중 하나가 약하면 바로 개발하지 않고 범위를 다시 줄이거나 보류한다.

# Part VIII. Oracle — 무엇을 만들 것인가

## 20. Opportunity Tree

목표 성과에서 하위 기회를 펼친 다음 가장 가치 있는 문제를 고른다.

```text
목표: 심사 리드타임 단축
  ├─ 자료 찾는 시간
  ├─ 누락 확인 시간
  ├─ 초안 작성 시간
  └─ 근거 대조 시간
```

## 21. Assumption Test

가정 중 **틀리면 가장 치명적이고 가장 불확실한 것**을 골라 싸게 검증한다.

```text
가정: 담당자가 실제로 자료 찾기에 가장 많은 시간을 쓴다.
검증: 1주 동안 5명에게 최근 5건 처리 시간을 단계별로 기록하게 한다.
판정: 자료 찾기 비중이 일정 기준 이상이면 GO, 아니면 문제 재선정.
```

## 22. Build / Buy

- 차별화의 핵심 → 직접 Build
- 범용 기능 → 기존 API/도구 Buy
- 이미 조직 내부에 있는 기능 → 연동 우선 검토

"만들 수 있다"는 이유만으로 직접 만들지 않는다.

## 23. HITL — Human in the Loop

사람 개입 지점을 설계 단계에서 정한다.

특히 다음은 사람 승인 후보가 된다.

- 고객에게 직접 영향을 주는 발송
- 지급/승인/부결 같은 최종 판단
- 규제·책임이 큰 결정
- 근거가 불충분한 예외 케이스
- 데이터 누락/불확실 상태

## 24. Cost Simulation

모델 조합, 토큰 수, 캐시 전략, 호출량별 시나리오를 비교한다. 저비용 모델 우선·고비용 모델 제한 같은 정책을 숫자로 정당화한다.

## 25. GTM — 사내 확산

처음부터 전사 배포하지 않는다.

```text
첫 사용자(beachhead)
→ 반복 사용
→ 성공 사례
→ 인접 팀 확산
→ 표준 업무로 정착
```

# Part IX. Atlas — Agent 구조 설계

## 26. 3계층 아키텍처

```text
[Model]
추론·분류·생성
   ↓
[Tools]
MCP · API · DB · RAG · 계산기
   ↓
[Orchestration]
순서 · 분기 · 재시도 · 종료 · 사람 승인
```

층을 분리하면 모델을 바꿀 문제인지, 도구가 필요한 문제인지, 흐름이 잘못된 문제인지 구분하기 쉽다.

## 27. 오케스트레이션

대부분의 사내 Agent는 처음부터 멀티에이전트가 필요하지 않다.

- 단일 에이전트로 충분하면 단일 구조
- 작업 성격이 명확히 분리되고 독립 검증이 필요할 때만 순차/병렬 Agent 고려
- 복잡도 자체가 비용이라는 점을 기억

## 28. Router

요청 유형에 따라 도구나 처리 경로를 분리한다.

```text
약관 질문 → RAG/근거 검색
재무 계산 → 코드/계산 도구
일반 안내 → 경량 모델 응답
불확실/고위험 → 사람 확인 큐
```

## 29. Memory

무엇을 기억하고 무엇을 매번 새로 받을지 정책으로 정한다.

- 사용자 선호
- 승인된 과거 판단
- 실패 사례
- 반복 업무 규칙

반대로 오래된 대화 전체를 무조건 넣으면 컨텍스트가 오염될 수 있다.

## 30. Moat, Growth Loop, RAG

### Moat

복제하기 어려운 자산은 단순 데모가 아니라 **축적된 운영 판단, 도메인 데이터, 결정 로그, 실패 사례**다.

### Growth Loop

```text
사용 → 피드백 → 개선 → 더 나은 결과 → 더 많은 사용
```

### RAG

근거 문서가 필요한 업무에서만 사용한다.

- 약관
- 규정
- 지침
- 공시
- 사내 문서

RAG가 필요 없는 업무에 습관적으로 붙이지 않는다. 근거가 없으면 "확인 불가"로 빠지는 경로도 설계한다.

# Part XI. Argus와 Muse — 운영과 학습

## 37. 운영 지표

Agent의 성공을 대표하는 핵심 지표 하나와 보조 지표를 정한다.

예:

```text
North Star: 건당 평균 검토 시간 절감
보조: 근거 일치율, 수정률, 재시도율, 사람 승인 거절률
```

## 38. Reliability

금융/업무 Agent에서는 다음을 운영 지표로 본다.

- 오류율
- 환각률
- 근거 누락
- 다운타임
- 예외 처리 실패

## 39. Pre-mortem

```text
이 Agent가 6개월 뒤 실패했다고 가정하자.
가장 가능성 높은 실패 이유 5개는 무엇인가?
각 실패의 조기 신호와 예방 조치를 적어줘.
```

## 40. Burn Rate, A/B, Incident

- **Burn rate** — 운영비 소진 속도 추적
- **A/B** — 프롬프트·모델 버전을 데이터로 비교
- **Incident** — 사고 대응, 복구, 재발 방지 기록

## 41. Muse — 판단의 축적

운영에서 얻은 다음 정보가 다시 기획과 설계로 돌아간다.

- 어떤 요청에서 자주 실패하는가
- 어떤 근거가 부족했는가
- 사용자는 어디서 수정하는가
- 어떤 기능은 실제로 쓰이지 않는가
- 어떤 승인 기준이 반복되는가

이런 판단의 축적(TK)이 장기적으로 Agent의 진짜 해자가 된다.

## 43. 문제 정의는 기능명이 아니라 As-Is 문제로 시작한다

서류보완요청 → 재접수 구간에서 반복과 대기가 발생한다. 고객은 어떤 서류를 다시 제출해야 하는지 기다리고, 접수 담당자는 같은 누락 안내를 반복한다.

# Part XV. 안티패턴

## 50. 기획 안티패턴

| 안티패턴 | 왜 문제인가 | 수정 |
|---|---|---|
| Agent가 모든 것을 한다 | 구현·검증 불가능 | 핵심 기능 1~2개로 제한 |
| 문제 정의에 숫자가 없다 | 아이디어 수준에 머묾 | count/p90/재작업률 중 하나 이상 |
| 완료 정의가 감성적이다 | 끝났는지 판단 불가 | 더미 N건, 출력 파일, 검수 기준 |
| 기술 스택부터 정한다 | 도구가 문제보다 앞섬 | 문제 → 입력/출력 → 도구 |
| 실패 경로가 없다 | 실제 운영에서 위험 | 모름/불확실/입력 누락 → 사람 확인 큐 |
| 모든 후보에 RAG | 불필요한 복잡도·비용 | 근거 문서가 필요한 경우에만 |
| 최종 판단까지 자동화 | 책임·규제 위험 | 판단 전 자료 정리/초안으로 축소 |
| 안 만들 것을 기록하지 않음 | 범위가 다시 커짐 | Do-Not-Build와 이유 기록 |

## 51. 프롬프트 안티패턴

- 한 줄 던지고 끝내기

- 에러 여러 개를 한꺼번에 고치게 하기
- 실행하지 않고 "될 것 같다"는 설명만 믿기

# Part XVII. 90분 기획 워크숍

## 59. 한 바퀴 완주형 진행안

| 시간 | 활동 | 산출물 |
|---|---|---|
| 0~10분 | As-Is에서 병목·반복·대기 구간 1개 선택 | 문제 후보 1개 |
| 10~25분 | To-Be 워크플로우와 Agent 후보 연결 | Agent 후보명·대상 사용자 |
| 25~40분 | 문제 정의 한 문단 | 문제 정의 초안 |
| 40~55분 | 핵심 기능 1~2개, 보류/금지 결정 | 범위 표 |
| 55~70분 | 더미 데이터와 완료 정의 | 검증 기준·출력 파일 |
| 70~80분 | 도구·데이터를 필수/선택/보류로 분류 | 기술 선택 메모 |
| 80~90분 | 1분 공유 + D5 인계 | 공유 스크립트·Input/Process/Output |

또 다른 관점으로는 다음 순서를 사용할 수 있다.

```text
과제 후보
→ ICP
→ JTBD
→ 페인 증거 3개
→ 만들 것 / 안 만들 것
→ 3관문(증거·중복·비용)
→ 완료 정의
→ 1장 기획서
```

목표는 완벽한 기획서가 아니라 **근거가 있는 1차 기획서를 끝까지 한 바퀴 완주하는 것**이다.

## 60. 좋은 Agent 기획서 체크리스트

### 문제

- [ ] 기능명이 아니라 실제 업무 문제로 시작하는가?
- [ ] As-Is 수치가 하나 이상 있는가?
- [ ] "불편하다"가 아니라 시간·대기·재작업·누락으로 표현되는가?

### 사용자

- [ ] ICP가 `전 직원`, `모든 고객`처럼 너무 넓지 않은가?
- [ ] JTBD가 기능이 아니라 사용자가 끝내려는 일인가?

### 검증

- [ ] 미래 의견보다 과거 행동을 물었는가?
- [ ] 실제 우회 행동/수작업 증거가 있는가?
- [ ] 가장 약한 가정이 드러나 있는가?

### 범위

- [ ] 핵심 기능은 1~2개인가?
- [ ] 안 만들 것과 이유가 적혀 있는가?
- [ ] 최종 승인/지급/계약 같은 책임 단계는 사람에게 남아 있는가?

### 데이터·도구

- [ ] 공개/더미 데이터로 먼저 검증 가능한가?
- [ ] 문제 → 입력/출력 → 도구 순서로 결정했는가?
- [ ] RAG/MCP/멀티에이전트가 정말 필요한가?

### 완료 정의

- [ ] 더미 N건으로 테스트 가능한가?
- [ ] 정상·예외·실패 케이스가 있는가?
- [ ] 출력 파일/화면이 구체적인가?
- [ ] 불확실·입력 누락 시 대체 경로가 있는가?

### 운영

- [ ] 사람 승인 지점이 명확한가?
- [ ] 예상 비용을 계산했는가?
- [ ] 핵심 KPI가 하나 있는가?
- [ ] 실패 로그와 결정 로그가 다음 버전에 남는가?

# Appendix B. 문서 전체를 관통하는 원칙 10개

1. **AI 출력보다 입력과 대화 품질을 먼저 관리한다.**
2. **바로 생성하지 않고 맥락과 분석을 먼저 둔다.**
3. **근거·불확실성·반박을 결과의 일부로 요구한다.**
4. **사용자 범위를 좁히고 기능이 아닌 JTBD를 정의한다.**
5. **페인은 의견보다 실제 과거 행동으로 검증한다.**
6. **핵심 기능을 1~2개로 줄이고 나머지는 이유와 함께 보류한다.**
7. **자동화보다 사람 판단 전 단계의 낭비를 줄인다.**
8. **HOW보다 WHETHER: 증거·중복·비용을 먼저 본다.**
9. **더미 데이터로 실제 happy path를 실행하고 완료 기준으로 검증한다.**
10. **운영 판단과 실패 로그를 남겨 다음 버전의 지식 자산으로 만든다.**
